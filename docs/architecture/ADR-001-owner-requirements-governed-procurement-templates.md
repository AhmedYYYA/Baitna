## 1) القرار الجوهري المعتمد

تعتمد «بيتنا» **ملف متطلبات المالك الموحد — Owner Requirements Brief (ORB)** بوصفه مصدر البيانات الأساسي المشترك، وتُنشأ منه وثائق **RFI / RFP / RFQ** المهنية وفق غرض الطلب ومرحلة نضج المشروع، بالاستناد إلى:

1. **قوالب قياسية محكومة — Governed Standard Templates:** بنية متسقة وبنود إجرائية وتعاقدية معيارية مراجعَة قانونياً وفنياً، لا تُترك للتحرير الحر من المالك.
2. **مكتبة اشتراطات بحسب الاختصاص — Jurisdiction-Specific Rules Library:** الإمارة، الموقع، السلطة المحلية المختصة، نوع المشروع، وتاريخ سريان النص المرجعي. التحقق من المصدر والتاريخ والمراجعة المختصة شرط قبل اعتبار البند واجب التطبيق.
3. **متطلبات خاصة بالمالك — Owner-Specific Requirements:** تفاصيل المسكن ونطاق الأعمال والميزانية ومستوى المواصفات والأولويات والجدول المتوقع والخدمات والملحقات.

**المبدأ:** القالب قياسي في الهيكل والحوكمة، وقابل للتخصيص في المحتوى دون تجاوز الاشتراطات الملزمة أو إضفاء اعتماد قانوني غير قائم. يُبرز النظام التناقضات ويطلب مراجعة اختصاصية، لا يُغيّر قواعد ملزمة تلقائياً.

## 2) التعريفات الرسمية بالعربية والإنجليزية

| الاختصار | English | العربية | الاستخدام |
|---|---|---|---|
| RFI | Request for Information | طلب معلومات | استطلاع السوق والمؤهلات والحلول والقدرات والخبرات. |
| RFP | Request for Proposal | طلب تقديم عروض (فنية وتجارية) | طلب المنهجيات والتصاميم أو الحلول والبرنامج والتكلفة ومعايير التقييم. |
| RFQ | Request for Quotation | طلب عرض سعر / طلب عروض أسعار | استدراج تسعير محدد لنطاق وكميات ومواصفات محددة. |

**ليست RFI → RFP → RFQ خطوات إلزامية متسلسلة**؛ تختار المنصة الوثيقة أو الجمع بينها طبقاً لوضوح النطاق وحاجة المالك وطبيعة الشراء. يُفصل RFI الخاص بالطرح التجاري عن RFI الفني المستخدم أثناء البناء لطلب الاستيضاحات.

في RFQ، يُميّز صراحةً بين **Budgetary Quotation — عرض سعر تقديري** و **Firm Quotation — عرض سعر تفصيلي/ملزم وفق الشروط المتفق عليها**؛ ولا يعد التقدير سعراً نهائياً متعاقداً عليه.

## 3) تجربة المالك

يُدخل المالك بياناته **مرة واحدة** باستخدام استبيان توجيهي مبسط ومتفرع بحسب الاختيارات (Guided Owner Requirements Brief)، مثل:

- الإمارة، المنطقة، موقع الأرض أو المشروع والجهة المختصة، ونوع المشروع.
- نوع المسكن، المساحة، الطوابق، الغرف والملاحق، والاحتياجات الخاصة.
- الميزانية والنطاق والسقف المتوقع وتفضيلات مستوى التشطيبات.
- الخدمات المطلوبة: التصميم، والاستشارات، والإشراف، والمقاولات، والتوريد والصيانة.
- أولويات التقييم: الجودة والكلفة والبرنامج والضمان والخبرة.
- الخيارات الخاصة (كالمجلس والمسبح والمصعد والمنزل الذكي) مع ظهور أسئلة إضافية عند اختيارها فقط.

لا يُطلب من المالك تحرير البنود القانونية القياسية. يُعرض له ملخص قابل للمراجعة، وأسباب إدراج الملحقات التنظيمية والفنية، قبل إصدار الوثيقة. يتاح وضع مبسط للمالك، ووضع مهني للاستشاري/مدير المشروع، **بالبيانات والمرجعية نفسيهما وصلاحيات تحرير مختلفة**.

## 4) محرك الوثائق وحوكمتها

كل مستند مُولَّد يتضمن: رقم الطلب؛ نوع الأداة؛ الإصدار؛ تاريخ الإنشاء؛ حالة المسودة/الإصدار؛ مصدر مدخلات المالك؛ نطاق المشروع؛ الإمارة والجهة المرجعية؛ قائمة البنود القياسية؛ البنود المحلية الخاصة؛ الملاحق الفنية والسعرية؛ قواعد الاستيضاحات والإغلاق والتقييم؛ تعارضات تتطلب مراجعة؛ سجل الموافقات والتعديلات.

- البنود القياسية: إصدارات مراجعَة من خبراء قانونيين وفنيين، مع أسباب الاستثناءات والاعتمادات.
- البنود المحلية: مصدر رسمي قابل للتتبع، تاريخ سريان وتحديث، وتعيين الاختصاص بموجب مكان المشروع ونوعه؛ لا تفترض المنصة توحيد متطلبات جميع الإمارات.
- المرفقات الفنية: مدخلات المالك والمخططات ومواصفات/BOQ التقديرية أو المبدئية حسب جاهزية المشروع.
- صلاحيات إصدار/تعديل/إغلاق الطلب وتقييم العروض وفق دور المالك/الاستشاري/مدير المشروع.
- حفظ عروض الموردين والردود منفصلة وسرية مع سجل نسخ، ومنع اطلاع المتنافسين على عروض بعضهم.
- لا تُنشئ نتيجة التقييم عقداً ملزماً تلقائياً ولا تعتمد SOW أو IMS بمجرد اختيار العرض.

## 5) الربط مع بقية منصة بيتنا

**Home ID (دائم) → Project → Owner Requirements Brief (ORB) → Procurement Package → RFI / RFP / RFQ → Clarifications & Submissions → Technical/Commercial Evaluation → Award Recommendation → Contract (مستقل) + SOW (مستقل) + WBS/BOQ → IMS (جدول رئيسي واحد وإصدارات معتمدة) → Site Evidence → Handover → Digital Home Passport / Maintenance.**

يجوز إعداد مسودة SOW وBOQ وبرنامج أولي في مرحلة الطرح؛ لكنها **لا تصبح** النسخ التعاقدية أو خط أساس IMS المعتمد إلا بعد موافقات مستقلة. يحتفظ النظام بإمكانية تتبع: ما طلبه المالك، وما قدمه المتنافسون، وما تم الاتفاق عليه، وما نُفذ لاحقاً.

## 6) الحدود والمخاطر غير المعتمدة تنفيذياً

- لا يوجد حتى تاريخه محرك إنتاجي لقوالب RFI/RFP/RFQ خاضع لمراجعة قانونية لكل إمارة.
- لا توجد شراكات أو اعتمادات رسمية يُفترض قيامها تلقائياً، ولا تكامل تلقائي مع الجهات الحكومية.
- النموذج الحالي المنشور على GitHub Pages للتجربة فقط، ولا يصلح لتخزين ملفات ملاك أو مقاولين حقيقية أو توقيع عقود.
- لا يجوز الادعاء بأن جميع النماذج «متوافقة قانونياً» قبل تأكيد القالب ومكتبة المرجعيات بواسطة مختصين مؤهلين، وتطبيق ضبط الإصدارات والأمن والخصوصية.

## 7) مخرجات المرحلة التالية المعتمدة للتصميم (قبل البرمجة)

1. **ORB Data Dictionary & Conditional Questionnaire:** قائمة حقول ملف المالك، الإلزامية والمشروطة، مصدر كل حقل وأذونات تعديله.
2. **Three Controlled Template Schemas:** هيكل قياسي مستقل لكل من RFI وRFP وRFQ، ووصف البنود والمرفقات والمراجعات اللازمة.
3. **Jurisdiction Rule Mapping:** مصفوفة الإمارة/الجهة/نوع المشروع، ومصادر النصوص وتاريخ المراجعة ودرجة الإلزام.
4. **Document Generation & Review Workflow:** توليد مسودة، كشف النواقص والتعارضات، مراجعة مهنية، إصدار، استيضاح، استلام، تقييم وترسية/إلغاء.
5. **Evaluation-to-Contract Traceability:** تحديد الترحيل للبيانات والملحقات بعد اختيار العرض، وآلية اعتماد العقد وSOW وIMS كل على حدة.
6. **Acceptance Criteria:** حالات اختبار للاختيار بين RFI/RFP/RFQ، وأسئلة المالك المتفرعة، وصلاحيات تعديل البنود، ومنع كشف أسعار المنافسين، وتاريخ الإصدار والإمارة.

**وضع الاعتماد:** قرار منتج رسمي داخل مشروع BAITNA لا يعني إقرار الصياغة النهائية للنماذج أو الالتزام القانوني بها أو اكتمال الوظيفة البرمجية.
